== Overview

The Severinno Marketplace searches for providers within a geographic radius.
Two distance-computation strategies are available:

* **PostGIS** — spatial SQL queries using the PostGIS extension (`ST_DWithin` + `ST_Distance`)
* **Haversine JS** — pure-JavaScript spherical trigonometry computed on the application server

The system uses a three-tier fallback chain:

.PostGIS → Haversine → null distance fallback
[source]
----
User provides lat/lng
        │
        ▼
┌─────────────────────────────────────────────────────┐
│  PostGIS available?   ──── No ───► Haversine JS     │
│  (isPostGISAvailable)           (computeDistanceMap)│
└──────────────────────┬──────────────────────────────┘
                       │ Yes
                       ▼
┌─────────────────────────────────────────────────────┐
│  ST_DWithin radius filter  (GiST-indexed)           │
│  + ST_Distance computation  (batch, one query)      │
│                                                      │
│  ┌──────────────────────────────────────────────┐   │
│  │  PostGIS query succeeds?  ─── No ──► Catch   │   │
│  │  (catch block in           │     └────┬──────┘   │
│  │   computeDistanceMap)      │          ▼          │
│  │                            │   Haversine JS      │
│  │                            │   fallback per-item │
│  └────────────────────────────┘                     │
│                                                      │
│         ▼                                            │
│   Both fail ──► distance_km = null                  │
└─────────────────────────────────────────────────────┘
----

=== Request Pipeline

The route handler at `GET /api/providers` follows a two-phase architecture:

==== Phase 1 — Resolve matching provider IDs

. Parse query params: `lat`, `lng`, `q`, `categoryId`, `radius`, `sort`, `page`, `limit`
. Check PostGIS availability via `isPostGISAvailable()` (Redis-cached, 5 min TTL)
. Build `centerGeo` when PostGIS + user geo + radius are all available

If **PostGIS path**:
.... Create `cachedRadiusCountFn` via `createCachedRadiusCountFn` — wraps Redis + raw SQL COUNT
.... Call `findEffectiveRadius(radiusKm, countFn)` — tries [userRadius, 5, 10, 25, 50, 100] km
.... If providers found: resolve paginated IDs with ST_DWithin + ORDER BY
.... If not found: try unrestricted fallback (`fetchUnrestrictedResults`)
If **non-PostGIS path**:
.... Count without spatial filter, resolve IDs, skip radius expansion

==== Phase 2 — Fetch full data

. `fetchProvidersData(providerIds, geo, deps)` runs three parallel queries:
.. Services (`service.findMany` — active, ordered by basePrice)
.. Completed bookings count (`booking.groupBy` — status COMPLETED)
.. Provider profiles (`user.findMany` — lightweight select)
. `computeDistanceMap` computes distance for each provider (PostGIS → Haversine → null)
. Map results to response shape (services grouped by provider, distances rounded to 1 decimal)

==== Key Insight

Haversine JS is **~70× faster per call** than a single PostGIS `ST_Distance`
evaluation. There is NO positive N at which PostGIS catches up in pure math
throughput.

PostGIS **wins by filtering before computing**: the GiST index scans O(log N)
candidates via `ST_DWithin`, then computes `ST_Distance` only for the filtered
subset — all in a single query round-trip.

== Decision Tree

The route handler uses this decision logic at `providers/route.ts`:

.Decision tree for geographic provider search
[source,plantuml]
----
@startuml
start

:Parse lat/lng/radius/params;

if (hasGeo && radius is finite) then (yes)
  :isPostGISAvailable();

  if (PostGIS available) then (yes)
    :Build centerGeo with user radius;
    :Create cached radius count function;
    :findEffectiveRadius(userRadius, countFn);

    if (effectiveRadius !== null) then (found)
      :Set expandedRadius if changed;
      :Phase 1b — resolve paginated IDs
       with ST_DWithin + ORDER BY;
    else (not found)
      :Phase 1b — unrestricted fallback
       (no radius filter);

      if (fallbackTotal > 0) then (yes)
        :Return unrestricted results
         with expandedRadius = -1;
        stop
      endif

      :Return empty (total=0);
      stop
    endif
  else (no PostGIS)
    :Count without spatial filter;

    if (total === 0) then (empty)
      :Return empty;
      stop
    endif

    :Phase 1b — resolve IDs
     (no spatial filter);
  endif
else (no geo)
  :Count all providers without radius;

  if (total === 0) then (empty)
    :Return empty;
    stop
  endif

  :Phase 1b — resolve IDs;
endif

:Phase 2 — fetchProvidersData
 (services + bookings + profiles
  in parallel);

:computeDistanceMap
 (PostGIS → Haversine → null);

:Return response with
 items + total + expandedRadius;

stop
@enduml
----

=== Crossover Threshold Analysis

The crossover point (where PostGIS becomes faster than Haversine) depends on
selectivity `s = (radius / spread)²`:

.T_postGIS(N, s) = 2000 + 22 × N × s  µs
.T_haversine(N)  = 20 × N + 0.3 × N    µs

[cols="3,3,3,3", options="header"]
|===
| Radius | Selectivity | Crossover N | Note
| 5 km | 0.25% | ≥ 99 | PostGIS always wins
| 10 km | 1% | ≥ 100 | PostGIS always wins
| 25 km | 6.25% | ≥ 107 | PostGIS always wins
| 50 km | 25% | ≥ 133 | PostGIS wins at any real scale
| 100 km | 100% | Never | Empates at ~15 ms (both viable)
|===

At Severinno's current scale (hundreds to low-thousands of providers), PostGIS
is **always beneficial** because the route combines filtering + computation in
a single query, avoiding a separate round-trip for the distance step.

=== When to Use Each Strategy

[cols="2,2,3,3,3", options="header"]
|===
| Strategy | Radius | Providers | Latency | Best for
| PostGIS | Any | Any | ~10 ms | Primary path. Requires PostGIS extension.
| Haversine JS | Any | < 5 000 | ~0.1-1.1 ms | Fallback when PostGIS unavailable. Development/testing.
| Both (combined) | Narrow | High | ~10 ms | PostGIS filters, Haversine catches if PostGIS query fails.
|===

== Progressive Radius Expansion

When PostGIS is available and the user's requested radius returns zero
providers, the search expands automatically.

=== Expansion Steps

The `buildRadiiToTry(userRadiusKm)` function builds a monotonic sequence:

[source,typescript]
----
export const EXPANSION_STEPS = [5, 10, 25, 50, 100] as const

// buildRadiiToTry(10)  →  [10, 25, 50, 100]
// buildRadiiToTry(0)   →  [0, 5, 10, 25, 50, 100]
// buildRadiiToTry(200) →  [200]  (no expansion)
----

=== Response Semantics

[cols="2,5", options="header"]
|===
| `expandedRadius` | Meaning
| `null` | The user's requested radius found providers (no expansion needed)
| `5`–`100` | Providers found after expanding to this radius
| `-1` | Providers exist but beyond 100 km (unrestricted fallback returned)
|=== 

=== Redis Caching

Each radius-level COUNT query is cached in Redis with a 2-minute TTL
(`DEFAULT_COUNT_CACHE_TTL = 120` seconds). The cache key encodes:

``` 
providers:count:{lat:.3f}:{lng:.3f}:{radiusKm}:{categories}:{query}
```

Coordinates are rounded to 3 decimal places (~110 m precision) so nearby
queries share a cache entry.

=== Caching Architecture

[cols="2,3,3", options="header"]
|===
| Cache | Key Pattern | TTL
| Radius count | `providers:count:...` | 120 s
| Proximity | `proximity:{lat}:{lng}:{radius}` | 60 s
| PostGIS available | `postgis:available` | 300 s
| Category descendants | `category:descendants:{id}` | 600 s
| Geo search (Nominatim) | `geo:search:{q}` | 86 400 s (24 h)
| Geo reverse | `geo:reverse:{lat}:{lng}` | 86 400 s (24 h)
| User-to-user distance | `distance:{uid1}:{uid2}` | 60 s
|===

== Distance Pipeline (Phase 2 Detail)

The `computeDistanceMap` function in `distance-fallback.ts` implements the
three-tier fallback:

=== Tier 1: PostGIS ST_Distance

One `$queryRawUnsafe` call for all provider IDs:

[source,sql]
----
SELECT id,
       ST_Distance(
         location,
         ST_SetSRID(ST_MakePoint($1, $2), 4326)::geography
       ) / 1000 AS distance_km
FROM "User"
WHERE id = ANY($3::text[])
----

This is a **batch query** — all distances in a single round-trip. The catch
block silently falls through to Haversine if this throws (e.g., PostGIS
extension temporarily unavailable).

=== Tier 2: Haversine JS (per-provider)

When PostGIS returns no result for a specific provider (or the batch query
failed entirely), Haversine is computed per-provider:

[source,typescript]
----
haversineKm(userLat, userLng, provider.lat, provider.lng)
----

=== Tier 3: null

When neither PostGIS result nor provider coordinates are available, the
distance is stored as `null` — the frontend renders `"—"`.

=== Error Isolation

IMPORTANT: The catch block in `computeDistanceMap` only catches the
`ST_Distance` query. Other queries in Phase 2 (`serviceFindMany`,
`bookingGroupBy`, `userFindMany`) are **not** inside this catch — errors
there propagate to the route's top-level `handleError`.

== Recommendations for Future Optimizations

=== Short Term (No Code Changes)

. **Baseline tracking** — Continue versioning `geo-baseline.json` and running
  comparisons in CI to catch regressions before deployment.

. **Benchmark granularity** — The current `geo-benchmark.mjs` tests 100/1 000/
  10 000 providers. For more precise tuning, add intermediate points
  (2 000, 5 000) to better match the production distribution.

=== Medium Term

. **Adaptive radius expansion** — The current expansion steps are fixed
  [5, 10, 25, 50, 100]. Consider making them configurable per category:
  dense urban categories (e.g., "Diarista") can start at 2 km; sparse rural
  categories (e.g., "Veterinário") can start at 20 km.

. **Two-tier Redis caching** — The radius COUNT cache (120 s TTL) could be
  extended with a pre-warm mechanism: when a new provider registers in a
  region, invalidate only that region's cache keys rather than waiting for
  TTL expiration.

. **Combine Phase 1b + Phase 2 into a single raw SQL** — Currently Phase 1b
  resolves IDs, then Phase 2 fetches data via Prisma. A single raw SQL with
  `SELECT DISTINCT ON + JOIN` could reduce round-trips for the PostGIS path.

=== Long Term

. **PostGIS on read replicas** — If Haversine fallback is ever triggered by
  database load (not unavailability), consider routing PostGIS queries to a
  dedicated read replica with PostGIS extension.

. **Geohash pre-filtering** — For ultra-low-latency requirements (< 5 ms),
  pre-compute geohash prefixes for each provider and index them with a
  B-tree. The route can filter by geohash prefix first, then refine with
  Haversine — avoiding the PostGIS fixed overhead (~10 ms) entirely.

. **Edge-case: provider clustering** — When many providers cluster in the
  same building (e.g., professional coworking spaces), the GiST index
  returns many tied-distance results. Consider adding a spatial
  regularization term (tiny jitter on insert) or a deterministic tiebreaker
  (favoriteCount) in the ORDER BY.

. **Materialized distance view** — For the most common distance queries
  (e.g., “show providers within 10 km of user”), maintain a materialized
  view with pre-computed distance buckets. Refresh on provider location
  changes.

=== C. Dependency Injection Pattern

All geo modules follow the same DI pattern for testability:

[source,typescript]
----
// Module exports a function that accepts injected dependencies
export async function computeDistanceMap(
  opts: ComputeDistanceMapOptions  // ← contains queryRawUnsafe, etc.
): Promise<Map<string, number | null>>

// Factory creates a configured function
export function createCachedRadiusCountFn(
  opts: CreateCachedRadiusCountFnOptions  // ← contains withCache, queryRawUnsafe, etc.
): RadiusCountFn                           // ← returned function is pure logic

// Pure function — no I/O, no dependencies
export function buildRadiiToTry(userRadiusKm: number): number[]
----

This pattern makes every module testable in isolation without database or
Redis connections. Each module has a corresponding test file in
`src/lib/__tests__/`.
